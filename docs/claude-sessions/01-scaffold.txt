     Context

     DESIGN.md describes a backend service with two pure, I/O-free functions
     that are meant to live in one shared domain module: the pending rule (§1
     "Pending Updates", §3.1) and the summary coverage check (§4 "Evaluation",
     §3.1/§3.3). The repo currently contains only DESIGN.md — no code, no
     tooling. This task scaffolds a minimal TypeScript + Vitest project with
     typed stubs for both functions and table-driven test files seeded with
     cases drawn straight from the design doc. The user will implement the
     function bodies; this step only sets up structure, types, and test tables.

     §4 was just updated: the coverage check now also requires every sentence to
     have at least one tag, not just that every diff entry is covered and every
     tag is real. The plan below reflects that.

⏺ Both implementations pass all 13 existing tests and typecheck cleanly. Here's
  the review.

  pending-rule.ts

  Matches design. The logic (latest > current && (declined === null || latest > 
  declined)) is a direct, literal translation of §1's rule, and the
  short-circuit on declinedVersion === null correctly avoids ever comparing
  against null. No concerns here — nothing to change.

  Edge cases the tests miss (none are bugs, just untested states):
  - currentVersion > latestVersion — shouldn't occur given the §1 assumption
    that versions only move forward, but the function handles it safely anyway
    (latest > current is false → not pending). Worth a test only if you want to
    document that this is the defined fallback for an inconsistent state, not an
    error.
  - declinedVersion === currentVersion or declinedVersion > latestVersion — both
    are states the system shouldn't produce, and the function's behavior for
    them is still sensible, but they're undocumented in §1. Not worth adding
    unless you want the test table to double as a spec for "can't happen"
    states.

  coverage-check.ts

  Matches design. All three §4 checks are present and independent: entry
  coverage, tag validity, and the new untagged-sentence rule. I traced all 8
  test cases by hand against the logic and they line up; the test run confirms
  it.

  Edge case the tests miss:
  - A sentence whose covers mixes a valid and an invalid id, e.g. covers: ["a", 
    "z"]. The code handles it correctly (contributes a to coverage, z to
    invalidTagEntryIds), but no test exercises a sentence that's simultaneously
    "useful" and "inventing." Worth a case since it's a realistic LLM failure
    mode (partially right tag), and today nothing proves the two concerns are
    tracked independently rather than one suppressing the other.
  - Duplicate ids within diffEntries itself (a data-quality case, not an LLM
    one) — if two entries shared an id, uncoveredEntryIds could report that id
    twice. Design doesn't say entry ids are unique, but it's implied by "diff
    entries" being distinct changes. Not worth guarding against in the pure
    function (the boundary that produces diffEntries should own that guarantee);
    flagging only so it's a conscious non-goal rather than an oversight.

  Things I'd change (style, not correctness):
  - taggedIds and invalidIds are built via two separate sentences.forEach passes
    over the same covers arrays. They could be computed in one pass (same loop,
    update both sets based on validIds.has(id)). Harmless at this scale — these
    are per-summary sentence lists, not hot paths — but it reads as two
    redundant traversals of the same data for no reason.
  - The final coverageCheckResult local variable is assigned and then
    immediately returned — could just return { passed, uncoveredEntryIds, 
    invalidTagEntryIds, untaggedSentenceIndexes } directly. Purely cosmetic.

  No findings that need fixing before this ships — the two style points are
  optional polish, and the missing edge cases are additional test coverage you
  may or may not want, not gaps in the implementation itself.
