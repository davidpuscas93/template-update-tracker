# Template Update Tracker: Design

## 1. High-Level Architecture

### Overview

Users need to see which of their engagement files have pending template updates. Loading an engagement takes about a minute, and that can't be changed. So the tracker has to know which engagements have pending updates without ever loading one.

Two systems already exist: **the product template database**, shared between all firms and fast to query, and **an engagement system per firm**, which is slow to load from.

We add one backend service, `template-update-tracker`. It keeps its own record of every engagement and the template version it is on, so it never needs to load one. The existing systems keep that record current by sending it events:

- the template database, when a new template version is published;
- the engagement system, when an engagement is created or opened, or an update is accepted or declined.

When a new version is published, every engagement on that template with an older version has a pending update. The user's screen asks the tracker for that list through an API.

The tracker's tables:

```
engagements  engagement_id, firm_id, template_id, current_version, declined_version, declined_at
templates    template_id, latest_version
summaries    template_id, from_version, to_version, summary_text, status, model_id, generated_at
```



### Pending Updates

When a user hasn't decided on several updates in a row, they are treated as one: accepting always moves the engagement to the latest version, and the summary covers the whole jump (e.g. v3 -> v5) rather than one summary per version.

When a user declines an update, the tracker records it: each engagement row also stores the latest version the user declined. **An engagement has a pending update when the latest published version is newer than both its current version and its declined version**:

- v5 is published, the engagement file is on v3, nothing declined -> pending
- the user declines v5; latest is v5 -> not pending
- v6 is published; v6 is newer than both -> pending again

Declining doesn't hide later updates, but accepting v6 would still bring in v5's changes, so the screen shows a note alongside the summary: *Includes changes from v5, which you declined on 12 Oct.*

### Change Summaries

Summaries are generated by an LLM from the JSON diff when a version is published, once for each older version still in use, and stored. Because templates are shared, a summary is shared by every firm with engagements on that version. Publishing happens about once a week per product template, so this is a handful of LLM calls per week. If generation fails at publish time, the summary is generated the first time a user requests it.

### Assumptions

- Accepting an update always moves an engagement to the latest template version. Accepting up to an intermediate version (e.g. v3 -> v4 while v5 exists) is plausible, for example when a newer version introduces a standard not yet in effect. The design supports it, since summaries are stored per version pair and the accept event can carry a target version, but this would be out of scope for v1.
- Summaries describe changes to the template itself, not how they interact with edits a firm has made to its own engagements.
- The existing systems emit an event only after the action has been committed (an accept is reported once the engagement is actually on the new version). An engagement's real version therefore only ever increases, which is what makes forward-only updates safe.


### Where It Runs


| Piece                 | AWS service                | Why                                                                                                                                                      |
| --------------------- | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Event intake          | EventBridge -> SQS         | Decouples both producers from the tracker. If the tracker is down, events wait in the queue; repeated failures go to a dead-letter queue for inspection. |
| Tracker logic and API | Lambda, behind API Gateway | Traffic is limited (weekly publishes, occasional decisions), so there's no reason to keep a server running.                                              |
| The three tables      | RDS PostgreSQL             | The core query, engagements on a template below a version, is an indexed `WHERE` on (`template_id`, `current_version`). Relational and small.            |
| Summary generation    | Bedrock                    | Template content stays inside the AWS account, which matters for a compliance-focused product.                                                           |




## 2. Implementation Plan



### Phase 1 - Pending List

Event intake (template published, engagement created, opened, accepted, declined), the `engagements` and `templates` tables, and the API. The screen shows a badge on engagements with pending updates. The `engagements` table starts empty, so it is filled two ways: an "engagement opened" event (the engagement system already pays the load cost when a user opens one), and a one-off background backfill for engagements nobody opens. Until an engagement is seen, it shows as "status unknown", never as "up to date".
*Users gain:* an at-a-glance view of what needs attention.

### Phase 2 - Change Summaries

Bedrock generation at publish time, the coverage check with its mechanical-list fallback, content team review, summary storage, and on-request fallback.
*Users gain:* they can decide without reading raw template changes.

### Phase 3 - Refinements

The previously-declined note alongside summaries, the "this summary is wrong" action, and accepting up to an intermediate version if it's wanted.
*Users gain:* they know when an update includes changes they already rejected, and can flag a wrong summary.

Phases 1 and 2 can be built in parallel: the core of summary generation (template diff in, readable text out) needs only the template database. It reads the `engagements` table only to choose which version pairs to generate, which is a small query once Phase 1 lands.

## 3. Testing Strategy

Most bugs in such a system live where the pieces meet: event handlers, the DB, the queue. So most tests will be integration tests.

1. **Unit tests: the pure logic**. Two pieces have no I/O: the pending rule (given the latest, current and declined versions, return pending or not) and the summary coverage check (given the diff entries and the LLM's tags, pass or fail). Both are tested as tables of cases: for the rule, the three from section 1 plus equal versions and nothing declined; for the check, a missing entry and a tag that points nowhere.
2. **Integration tests: event handling and the API**. The tracker runs against a real Postgres (Testcontainers). Each test sends an event and checks the resulting row and API response. Two cases matter most:
   - the same event delivered twice changes nothing (SQS can deliver duplicates);
   - events arriving out of order never move a version backwards (SQS does not guarantee order).
3. **Summaries**. Within the integration tests, Bedrock is replaced by a fake LLM that returns fixed text, so tests are fast, free and repeatable. They check that the right version pairs are generated on publish, that the on-request fallback works when generation fails, and that a summary failing the coverage check twice falls back to the mechanical list. Whether the text itself is good can't be asserted in a test; that is covered in section 4.



## 4. Evaluation & Observability



### Evaluation

A summary can fail in two ways: **invention** (it describes a change that isn't in the diff) and **omission** (it leaves out one that is). Omission is worse for an auditor, because nothing on screen hints at a change they never saw. Unlike most LLM tasks, this one has ground truth: the JSON diff says exactly what has changed. Evaluation has three layers:

- **Automated check, on every summary**. The LLM tags each sentence with the diff entries it describes. Plain code, not another LLM, then checks that every diff entry is covered and that every tag points to a real entry. On failure it retries once; if that fails too, users see a mechanical list of changes rendered directly from the diff. Less readable, but never wrong. This check proves every change is mentioned, not that each is described correctly; that is what the next two layers are for.
- **Content team review**. The team that published the change reviews its summaries afterwards and can reject one (recorded in its `status`), which falls back to the mechanical list. With about one publish a week per template, this is realistic.
- **User feedback**. A "this summary is wrong" action on the screen, tracked per `model_id`, so a model change that makes summaries worse shows up quickly.



### Observability

Errors surface on their own. The bigger risk in this design is data that is silently wrong: an engagement showing the wrong status with nothing failing. Each signal below answers "how would we find out?" for one way that can happen. Metrics and alarms live in CloudWatch.


| What goes wrong                                              | How we find out                                                                                                                                                                                         |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| An event fails repeatedly and lands in the dead-letter queue | Alarm when the dead-letter queue is not empty. Messages are replayed once the cause is fixed; handlers are idempotent, so this is safe.                                                                 |
| The tracker falls behind or stops                            | The age of the oldest message in the queue keeps rising.                                                                                                                                                |
| An event is lost without any error                           | Drift on open: when an "engagement opened" event reports a newer version than the tracker stored, the row is corrected and the mismatch counted. Mismatches per open measure how accurate the table is. |
| Summaries get worse, e.g. after a model change               | Coverage-check failures, mechanical-list fallbacks, rejections and user flags, per `model_id`.                                                                                                          |
| The backfill hasn't finished                                 | Share of engagements still in "status unknown".                                                                                                                                                         |


Every event carries a correlation ID from the system that emitted it, so one action, such as a user's accept, can be traced end to end. CloudWatch holds the metrics and alarms above; exceptions, with stack traces, go to an error tracker such as Sentry.

## 5. Failure Modes & Tradeoffs



### Failure Modes


| Failure                                                | Effect                                      | Mitigation                                                                                                     |
| ------------------------------------------------------ | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Duplicate event (SQS delivers at least once)           | The same change applied twice               | Handlers are idempotent upserts; a repeat changes nothing.                                                     |
| Events out of order                                    | An old event could move a version backwards | Updates only move forward: `UPDATE ... WHERE current_version < $new`.                                          |
| Producer never sends an event                          | A row stays wrong, with no error anywhere   | Corrected on the next open; caught by the drift metric.                                                        |
| Bedrock unavailable, or a diff too large for one call | No summary | Large diffs are split by template section. If Bedrock is down, generation is retried on first request (section 1), with the mechanical list shown until it succeeds. |
| Backfill competes with users for the engagement system | Slower opens for real users                 | Backfill is rate-limited and runs off-hours.                                                                   |
| Many Lambdas each open a Postgres connection           | Connection limit exhausted                  | RDS Proxy pools connections. Not expected at this traffic, but cheap insurance.                                |
| One tracker database holds every firm's data           | A query leaks another firm's engagements    | Every query is scoped by `firm_id`; the tracker stores only IDs and version numbers, never engagement content. |

### Tradeoffs

- **A separate record instead of reading engagements**. The tracker's copy can lag or briefly be wrong, which drift detection measures; the alternative is a one-minute load per engagement.
- **Summaries generated at publish, not on demand**. Some may be generated for engagements nobody opens, but users never wait, and at one publish a week the cost is negligible.
- **LLM summaries over a plain list of changes**. Readable for non-technical users, at the risk of errors, which the coverage check, review and mechanical-list fallback contain.
- **Latest-only accept**. Simpler model and UI; intermediate versions are deferred (see Assumptions).
- **Lambda and RDS over containers or DynamoDB**. No idle servers and plain SQL queries, at the cost of cold starts and the need for connection pooling.
